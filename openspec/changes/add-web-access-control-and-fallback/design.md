## Context

当前聊天链路为 `ChatInput -> chat store -> POST /api/chat/stream -> ChatService -> ContextBuilder/McpManager/LlmClient`。`ContextBuilder` 会向模型暴露该用户所有已连接 MCP 工具，`ChatService` 在模型发起调用后直接按工具名执行。现有 MCP 服务只有启用状态，没有“是否会访问外网”的属性，因此仅在前端隐藏开关或在系统提示词中声明禁止联网都不是可靠的权限边界。

异常处理分散在多个层级：记忆与文档检索部分已有 best-effort 降级；MCP 调用把失败包装成工具结果；LLM 流异常则直接输出原始异常文本。需要在不引入特定搜索供应商的前提下，形成统一、可观测、不会绕过联网许可的执行策略。

## Goals / Non-Goals

**Goals:**

- 支持用户对每次消息明确允许或禁止网络工具，默认安全且兼容旧客户端。
- 同时在工具发现和工具执行两处强制联网策略，避免模型幻觉、旧上下文或伪造请求绕过。
- 对 LLM、网络工具、检索和 SSE 故障采用可预测的重试/降级策略，尽量返回可用答案或可操作反馈。
- 向前端提供稳定错误码和降级元数据，同时保持 SSE token/done 基本协议兼容。
- 复用现有 MCP 架构，允许任意搜索/浏览 MCP 作为联网能力接入。

**Non-Goals:**

- 不内置搜索引擎、抓取器或特定供应商 API。
- 不承诺关闭单次“联网回答”后停止所有后台网络活动；已配置 MCP 的健康检查/重连仍由服务级启用状态控制。
- 不对所有 MCP stdio 工具自动判断其网络行为，也不把模型 API、数据库、Qdrant/Neo4j 访问归入用户可见的联网开关。
- 不在首版自动续写已经输出一部分的流式答案，避免重复内容和语义错位。

## Decisions

### 1. 联网开关是单次请求策略，默认关闭

`ChatRequest` 增加 `allow_network: bool = false`，`send` 与 `stream` 都显式传递到上下文构建和工具执行。输入框旁提供开关，并将最近选择保存在浏览器本地；每次发出的用户消息在前端状态中保存当时的值，供重试复用。

选择单次请求而非仅做全局设置，是因为联网需求通常随问题变化，也能让历史请求的权限语义清晰。默认关闭让旧客户端和缺失字段的请求采取最小权限。

### 2. MCP 服务显式标注 `requires_network`

`mcp_servers` 增加非空布尔字段 `requires_network`。HTTP/SSE 传输的新服务默认 `true`，stdio 默认 `false`，但用户可在配置时修改，因为 stdio 进程也可能访问互联网，而 HTTP 服务也可能只是内网服务。

采用服务级标注而不是按工具名猜测，可解释、可迁移、不会因工具重命名失效。首版不做工具级覆盖，以控制数据模型和 UI 复杂度。

### 3. 工具发现过滤 + 执行时授权双重校验

`McpManager.openai_tools(user_id, allow_network)` 在联网关闭时排除 `requires_network=true` 服务的全部工具；工具路由同时携带 `server_id` 与联网属性。`execute_tool(..., allow_network)` 在入队前再次读取/校验路由策略，拒绝未授权网络工具并返回稳定的 `network_access_denied` 错误。

第一层降低模型误调用概率，第二层才是安全边界。只用系统提示词或只过滤 tools 都不足以抵抗旧上下文、内部调用错误和后续代码回归。

### 4. 用阶段化异常策略替代统一 catch

异常按阶段处理：

| 阶段 | 策略 | 对用户结果 |
| --- | --- | --- |
| 记忆/个人文档检索 | 隔离异常并继续 | 本地上下文减少，`done.degradations` 标注对应能力不可用 |
| 网络 MCP 工具 | 将结构化失败送回模型 | 模型基于已有上下文回答，并明确未取得网络结果 |
| 工具循环达到上限 | 追加收尾指令并做一次无工具调用 | 返回已获得结果的总结；仍失败则进入 LLM 兜底 |
| LLM 首 token 前的超时、限流、5xx、连接失败 | 指数退避加随机抖动，最多重试 2 次 | 成功则正常输出；耗尽后返回结构化错误 |
| LLM 认证/参数/4xx | 不重试 | 返回不可恢复错误，不暴露上游原文 |
| LLM 已输出 token 后中断 | 不自动重放 | 保存部分回答为 `interrupted`，返回可重试错误 |

网络工具失败后不直接终止整个回答，因为工具结果协议本就允许模型理解失败；系统提示词会要求模型披露“联网检索失败，以下基于本地信息”。

### 5. SSE 错误和完成事件携带结构化状态

保留 `token`、`done`、`error` 事件名。`error` 数据统一为 `code`、`message`、`recoverable`、`request_id`、`partial_saved`；`done` 增加 `degraded: bool` 和 `degradations: string[]`。前端只展示后端映射后的用户信息，不展示异常类、URL、Header 或供应商响应体。

为避免把“回答成功但部分能力不可用”误报成红色错误，降级信息随 `done` 返回，并在消息气泡显示非阻塞提示。真正无法完成回答才发 `error`。

### 6. 重试重放原请求，而不是续接旧 SSE

前端对 `recoverable=true` 显示“重试”按钮，使用原始用户内容、会话 ID 和当时的 `allow_network` 重新发起请求。为防止历史中出现重复用户消息，后端请求增加可选 `client_request_id`，同一用户/会话下重复 ID 复用已落库的用户消息；首版可先实现前端避免并发，再在数据库增加幂等键完成可靠重试。

### 7. 配置化重试与安全日志

增加 `LLM_REQUEST_TIMEOUT_SECONDS`、`LLM_MAX_RETRIES`、`LLM_RETRY_BASE_SECONDS`，设置严格范围。每个请求生成 `request_id`，日志记录阶段、错误码、尝试次数、会话/用户的不可逆摘要和耗时；不记录密钥、Cookie、MCP Header、完整消息和工具参数。指标至少覆盖请求成功率、降级率、各错误码、重试成功率和网络工具耗时。

## Risks / Trade-offs

- [MCP 服务被错误标成“不联网”仍可通过 stdio 出网] → UI 明示该字段是安全属性；HTTP/SSE 默认联网；管理员部署可进一步限制 stdio 进程网络，并在后续支持管理员锁定。
- [联网关闭不等于应用完全离线] → 产品文案使用“允许本次回答调用网络工具”，并在帮助文本中说明模型服务和后台连接不受该开关控制。
- [LLM 重试增加延迟和成本] → 仅对首 token 前的瞬时错误重试，次数与退避可配置，并记录重试指标。
- [工具失败后模型可能仍声称已联网] → 工具失败使用稳定结构，并在系统提示中要求披露失败；增加行为测试验证输出约束。
- [SSE 结构扩展影响旧前端] → 保留事件名与 `message` 字段，新增字段均为附加字段；分阶段先部署后端再部署前端。
- [幂等重试需要数据模型变化] → 以客户端 UUID + 用户/会话唯一约束实现，冲突时查询并复用，不依赖内存锁。

## Migration Plan

1. 增加数据库字段与后端兼容逻辑；迁移时将 HTTP/SSE 服务设为 `requires_network=true`，stdio 设为 `false`。
2. 部署后端，缺省 `allow_network=false`，接受旧前端请求，并让扩展后的 SSE 仍含原 `message` 字段。
3. 部署 MCP 设置 UI 和聊天开关；对现有 stdio 服务提示用户复核联网属性。
4. 开启结构化指标观察降级率、错误码和重试放大量，再按实际数据调整重试参数。
5. 回滚时先回滚前端，再回滚后端；数据库新增字段保持不删，避免破坏旧版本运行。

## Open Questions

- 产品文案最终采用“联网”还是更准确的“允许网络工具”？建议界面显示“联网”，悬浮说明写清权限边界。
- 是否需要管理员级总开关强制全站禁网？本方案预留 `NETWORK_TOOLS_ENABLED` 配置，但首版以用户单次开关为主。
- 是否在本次实现中完成数据库幂等键，还是先用前端重试并把幂等作为第二阶段？建议同批完成，避免重试产生重复历史。
